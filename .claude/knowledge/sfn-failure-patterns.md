# Step Function Migration Failure Patterns

Known, previously-diagnosed failure patterns for the migration state machines. `/sfn-triage` classifies every new failure against this list **before** hypothesizing anything novel. When a triage session confirms a genuinely new pattern, append an entry here in the same format.

Entry format: **Signature** (what the failure looks like in the execution history / logs), **Root cause** (the confirmed mechanism, with evidence type), **Fix** (canonical remedy or PR reference).

---

## 1. Descope FGA 429 masked as 500

- **Signature**: Task state fails with a generic HTTP 500 from the authorization/FGA call path. The surfaced status is 500, but the raw error payload / downstream Descope response body shows rate limiting.
- **Root cause**: Descope FGA returns 429 (rate limit) under migration write bursts; an intermediate layer rewraps it as 500, so the execution history lies about the status. Never trust the surfaced HTTP status — pull the raw payload.
- **Fix**: retry with backoff on 429 at the FGA client, and/or reduce concurrent FGA writes. (Diagnosed against live dev/prod data, Jul 2026.)

## 2. DynamoDB write throttling (systemic, NOT transient)

- **Signature**: Migration lambda fails or slows with `ProvisionedThroughputExceededException` / throttled-write metrics on the target table; failures cluster across many entities in the same window.
- **Root cause**: Systemic write throttling from migration concurrency exceeding table capacity — historically mislabeled "transient" until CloudWatch throttle metrics proved it was sustained. Always check `WriteThrottleEvents` over the failure window before calling anything transient.
- **Fix**: retry/concurrency limits in the migration writer (shipped); verify table capacity mode before large batch runs.

## 3. Negative fee rate

- **Signature**: Financial migration state fails (or produces wrong figures) on entities whose fee/supplies rate is negative in source data.
- **Root cause**: Source data contains negative fee rates the transform did not anticipate; validation gap, not a pipeline error.
- **Fix**: validation/normalization in the fee transform; quantify affected entities via Athena before re-running.

## 4. Missing `partType`

- **Signature**: Parts migration state fails on records lacking the `partType` field.
- **Root cause**: Source parts records legitimately missing `partType`; mapper assumed presence.
- **Fix**: defaulting/skip logic in the parts mapper (shipped).

## 5. Missing `entity.json` contact fallback

- **Signature**: Entity migration fails or emits incomplete contact data for entities whose `entity.json` lacks primary contact fields.
- **Root cause**: No fallback when the primary contact block is absent in `entity.json`.
- **Fix**: contact fallback chain in the entity transform (shipped, verified against live dev/prod data).

## 6. Unrecognized SKU family → `subscription` missing from v6 `entitlements.json` (silent)

- **Signature**: Migration pipeline execution SUCCEEDS, but `mig-aps-mg-fun` cannot resolve `subscription.skuPack` for the entity. The transform-bucket `outbound/<entityId>/entitlements.json` is `AccountCreated.v6`-sourced and has no `subscription` key; its SKU codes belong to a family the producer's pack map doesn't know (e.g. `C-NEX-*` "Next" vs the original `C-HOR-*` "Horizon").
- **Root cause**: `int-create-account-fun`'s `PACK_BY_PREFIX` (src/services/entitlements-transform.ts) matches SKU-code prefixes case-sensitively; a SKU-family rename upstream makes `deriveHorizonSubscription` return undefined and the `subscription` key is omitted — silently, with the pipeline green. Confirmed against live prod S3: 6/52 outbound records affected, which was 100% of v6-sourced records (Aug 2026).
- **Fix**: add the new family's prefixes to `PACK_BY_PREFIX` (PRO before BASIC) + warn loudly when a v6 event yields no pack (shipped in int-create-account-fun). Existing affected entities need an explicit S3 rewrite + aps-step re-run — the entitlements writer is create-only and will not repair them on replay.

## 7. Oversized terminal Lambda return under loop-and-resume (`States.DataLimitExceeded`)

- **Signature**: A loop-and-resume task fails with `error: States.DataLimitExceeded`, `cause: "The state/task 'lambda' returned a result with a size exceeding the maximum number of bytes service limit."` The Lambda itself **SUCCEEDED** — check the `REPORT` line: the affected entity used 524 MB of 2048 MB and logged `migration COMPLETE with errors` before Step Functions discarded the response. The tell is that the loop's *intermediate* (`PARTIAL`) returns are ~1-2 KB and only the **final** (`COMPLETE`) return breaches, because the terminal return is the one carrying a cumulative per-record array. **Do not read this as an out-of-memory or disk-space problem** — it is purely the 262,144-byte SFN state-payload quota.
- **Root cause**: `mig-fin-mg-fun/src/index.ts` inlined an unbounded `failedRecords[]` in the terminal return; `getFinMappingOutcomes` reads the whole durable mapping table, so it accumulates across every iteration. Worst entity: 5,145 records × 90 B mean = **463,050 B vs the 262,144 B quota (1.77×)**; breach threshold ≈ 2,913 records. Measured blast radius: 3 executions in 1,057,023 DynamoDB records (3 entities) — rare, recurring, and a 21× outlier vs the next-worst entity. Confirmed live Aug 2026 and reproduced in a unit probe at 452,862 B.
- **`ResultSelector` cannot mitigate this.** It replaces the state's *raw result*, which must be ingested first — and ingestion is where the quota applies. The fix must reduce what the Lambda returns.
- **Fix**: claim-check — write the array to S3 (keyed by **execution**, not a fixed per-entity key, or an undo + re-migration misattributes evidence) and return `failedRecordCount` + an `s3://` ref + a 50-record sample. Three traps, all found by adversarial design review *before* coding:
  1. Derive the count from the reconciled `counts[*].failed`, **not** `failedRecords.length` — a failure that never persisted a FAILED row (IDIS-615) is real but absent from the array, so reading the array's length reports 0 and lets a wholly broken migration report success.
  2. Emit every new field **unconditionally, including zeros**. An absent JSONPath in a downstream `Choice`/`Parameters` raises `States.Runtime`, which is **not** catchable — and guard each rule with `IsPresent` anyway, so an execution in flight across the deploy boundary falls through instead of dying. Deploy the Lambda strictly before the state machine.
  3. Never ship the payload bound alone: the loader returns `COMPLETE`, so bounding the payload turns a loud failure into a **green migration** for an entity that lost 26% of its financials. Pair it with a failure-rate gate, and route that gate's status write through a `Pass` that synthesizes `$.error = {Error, Cause}` (the `Emit*` states read `$.error.Error`) — **not** through `WriteFailureStatus`, which rewrites `status = "FAILED"` on the same key and erases the new status.
- **Note**: `locals_sfn.tf`'s header comment claims `States.ALL` cannot catch `States.DataLimitExceeded`. The failing execution's history **refutes** that at a Lambda task: events 150→152 show the `States.ALL` Catch firing and routing to `WriteFailureStatus`, which wrote the quota message and reached `EmitMigrationFailed`. Don't add a redundant named tier on that basis; verify against an execution history first.

## 8. Downstream service makes a field immutable; the convergent upsert still sends it (hard 400 on re-run)

- **Signature**: A migration state fails with a **non-retryable 400** whose body names the mechanism in `details[*].messageId`, e.g. `"quantity cannot be changed via update — use the adjustQuantity endpoint"` with `requestedQuantity` / `currentQuantity`. The surfaced status is the REAL status here — unlike pattern 1, do not go looking for a masked 429. The tell is that the entity **already migrated successfully once**: check the mapping/status table for a prior `COMPLETED` row (`mig-migration-common-iac`, key `entityId`+`executionId`). First-time migrations pass, because CREATE may still set the field; only the UPDATE branch of a re-run breaks. Blast radius therefore looks tiny in logs while being ~100% of re-migrations whose source value moved.
- **Root cause**: The target service tightened a field to create-only and moved mutation to a dedicated endpoint. The migration client still puts the field in a shared create/update payload, so the PUT asks for a change the service now refuses. Confirmed for `prt-parts-svc` instance `quantity` (Aug 2026: an entity migrated Aug 21, then re-run Aug 26 after its source quantity changed). Dating the contract change: look for the new endpoint's QA cases in Jira (`QAC-22577`…`22587`, all Done 2026-08-13 — the day before the first failure). Same class as **DP-68** (`wor-work-order-svc` closed the migration-era `paidAt`/`invoiceId` exemption) and as `prt-parts-svc`'s immutable `initialCost`, which `updateCatalog` already strips.
- **Two traps**:
  1. **A shared create/update payload type is the root defect.** Fix it by *typing* the update shape as an omission (`Omit<CreatePayload, "field">`) and deriving it from the create builder by destructuring the field away — not by deleting a key at the call site. Then the compiler, not a reviewer, stops reintroduction, and a field later added to create cannot silently go missing on update.
  2. **Stripping the field alone converts a loud abort into a silent wrong-data success.** If the stripped field participates in the content hash (`instock` does), the next run hash-matches and SKIPs, latching the divergence as converged forever. Pair the strip with a persisted divergence marker (intended + stored, written as a pair, guarded on `typeof`, since 0 is a legitimate intent) plus a run-level census emitted **unconditionally including 0**. Reuse the `storedPartType` marker pattern in `part-processor.ts` — it exists for exactly this. Remember the DynamoDB marshal/unmarshal in `migration-mapping-service.ts` is hand-written: a new record field that is not added on **both** sides never persists, and the queue reads empty while the run reports divergences.
- **Fix**: strip-and-mark first (small, reversible, loud), then reconcile through the new endpoint as a separate reviewed layer. A delta endpoint like `adjustQuantity` is **non-idempotent** — a committed-but-timed-out call followed by a retry double-counts — so it needs the probe-first, no-500-retry discipline `createInstance` already uses, and convergence must come from re-reading current state, never from replaying a delta. That puts the reconciliation layer behind the design gate.

## 9. Zero-customer entity → SO transform hard-fails while customer transform succeeds with 0

- **Signature**: `mig-transform-common-iac-event-logger` fails with `TransformFailed` after the `TransformServiceOrder` Map iteration returns `{success: false, error: {errorType: "EntityNotFoundError", message: "No customers found for entity <id>", retryable: false}}`. The Lambda invoke itself is HTTP 200 (no masked 429 — checked against pattern 1); `CheckResult` routes the non-retryable payload error to `FailIteration`, aborting any still-running iterations. The tell: in the SAME execution, `TransformCustomer` **succeeded** minutes earlier with `statistics: {customersProcessed: 0}` and the transform bucket's `outbound/<entityId>/customers/` prefix is empty.
- **Root cause**: The entity genuinely has zero customers in the source data, and the two transforms disagree about whether that's valid: `mig-cust-transform-fun` treats it as success-with-zero, while `mig-so-transform-fun` (`src/index.ts:184`, present since original commit `cff8386` — a design decision, not a regression) throws non-retryable when `headerData.customers.length === 0`. Confirmed live in dev, Aug 2026: 4 of 6 FAILED executions Aug 20-28 were this signature (4 distinct entities), against 188 SUCCEEDED — recurring on every zero-customer entity enqueued headless, not transient.
- **Fix**: (pending — options triaged Aug 2026, no PR/ticket yet) either (A) tolerate zero customers in the SO transform with a WARN + explicit `zeroCustomerEntity: true` statistic (never silent-green), or (B) route `EntityNotFoundError` to a distinct SKIPPED status/failureCode in the state machine so it stops counting as a pipeline failure. Note the cross-account Athena role (`iso_forms_athena`) is NOT assumable from the SSO Admin role — corroborate zero-customer claims via the customer transform's own output + the S3 `customers/` prefix instead.

## 10. Stripe rejects a source-data field at payment-account creation (PO Box / phone / country class)

- **Signature**: `ImportFinancials` fails in Phase 0 with `FinProxyRequestError … payment-account … 500` whose cause embeds a Java stack ending at `PaymentAccountService.migratePaymentAccount(PaymentAccountService.java:530)` with `"Failure generating Stripe account via Lambda invocation"`. The 500 is a **triple mask**: the real error lives only in the **fin-stripe-fun** CloudWatch logs, e.g. `operation createAccountForMigration failed: Address can't be a Post Office Box (PO Box). Provide a physical address.; request-id: req_…` — a Stripe 400-class data rejection, NOT rate limiting (checked vs pattern 1) and NOT retryable, even though fin's IdempotencyService logs it as `Transient failure … releasing lock so a retry can re-run` (misclassification — retries on unchanged data can never succeed).
- **Root cause**: the entity's source data carries a field Stripe refuses for connected-account creation, passed through untouched by `mig-fin-mg-fun`'s `src/transformers/phase0.transformer.ts` (address: lines ~116-123, only a non-blank check). Known instances: PO Box in the PHYSICAL-role address (confirmed live prod Aug 2026, corroborated in transform-bucket `outbound/<entityId>/entity.json`); non-dialable phone (DP-39); invalid country (DP-1 Phase 1.5). Blast radius of the PO Box instance: 1 FAILED / 16 executions prod ≥2026-08-21; deterministic recurrence for every PO-Box-address entity (prevalence sample over the 31,242 outbound entity.json files pending).
- **Fix**: the shop precedent is "**send Stripe the field valid or not at all**" (DP-39 fix `f1dea07` for phone; prefill is best-effort, Stripe onboarding is the source of truth) — for a new instance, screen the field in `buildMigratePaymentAccount` and omit the prefill with a loud WARN + statistic, never a silent drop and never a hard abort where the field is optional. Data-only alternative: fix the source address and re-trigger via `start-execution` with the original input (redrive is useless — Fail-state terminal). Diagnose by going straight to fin-stripe-fun logs; never trust the surfaced 500 or the "transient" label.

## 11. Athena fan-out cost exceeds the 900 s Lambda ceiling (no slow query exists)

- **Signature**: `mig-transform-common-iac-event-logger` task fails `error: "Sandbox.Timedout"`, `"Task timed out after 900.00 seconds"` on `mig-fin-transform-fun`. `REPORT` shows low memory use (456/2048 MB) — **not** an OOM. Lambda logs appear full of 850 s queries, but `batch-get-query-execution` shows max engine 23 s / queue 0.1 s. The tell: logged `durationMs` includes semaphore wait because `startOperation` precedes `acquireQuerySlot` (`athena.service.ts:195` vs `:199`). Sandbox is reused across all 3 SFN attempts (one log stream, no `INIT_START`), so frozen in-flight queries resume and consume the next attempt's slots.
- **Root cause**: customer-ID chunking (`financial.service.ts:88`, `BATCH_SIZE = 500`) fans 13 loaders × ceil(C/500) chunks. The DMS `_current` tables have no `customerid`/`entityid` partitioning, so each chunk **full-scans** the table — identical per-chunk `DataScannedInBytes` across all 16 chunks proves it. An entity with 7,934 customers: 237 queries, 543.4 GB vs 34.0 GB once = **16.0× redundant**, 6,009 s serial. `ATHENA_MAX_CONCURRENT_QUERIES` defaults to **6** (env var unset live) while the real quota is **Active DML queries = 500**, so the floor is **1,002 s against a 900 s hard ceiling** (900 s is Lambda's maximum — the timeout cannot be raised). Confirmed dev Aug 2026. Blast radius: **56 of 9,370 entities ≥ 6,800 customers deterministically time out**, 84 more at risk, max 28,340.
- **Fix**: de-chunk — scope customer loaders with `customerid IN (SELECT customerid FROM fullbay_customer_current WHERE entityid = X)` instead of chunked IN-lists (237 → 42 queries, 543 → 34 GB). Raising `ATHENA_MAX_CONCURRENT_QUERIES` to 25 is a valid hotfix (floor → 240 s) but **does not fix the tail**: 28,340 customers still needs 844 s at concurrency 25. Note SFN retries `States.ALL` MaxAttempts 2 → 3 × 900 s = 45 min billed per doomed entity, so abort a timeout loop rather than letting it ride.
- **Generalizable lesson**: when a Lambda logs uniformly slow I/O, compare the logged duration against the *service's own* statistics before believing it. A semaphore in front of the timer turns queue depth into fake latency, and the real defect (redundant work) hides behind it.

## 12. `CurrencyPinError` on a FAILED payment-account row: the state machine never forwards `currencyPin`

- **Signature**: `ImportFinancials` (or the undo task) fails with `CurrencyPinError` saying `a payment-account row exists with status FAILED and no downstream id; fin-proxy may hold an account of unknown currency … re-run with currencyPin: { currencyCode, reason } on the Step Functions input`. Evidence: `pin=absent; paymentAccountRow=FAILED no newId`.
- **Root cause**: an earlier run's Phase 0 payment-account mint failed (often pattern 10, the Stripe PO Box rejection), leaving `mxfinpacct_<entityId>` FAILED with no `newId` and no `mxpin_fin_<entityId>` row. The currency gate (`mig-fin-mg-fun` `src/index.ts:723`) refuses because it can't prove what fin-proxy holds. The remediation text is misleading: the live `mig-migration-common-iac-event-logger` definition builds the Lambda Payload from only `entityId`/`resumeCursor`/`sfnExecutionId` (or `undo`), so a `currencyPin` on the execution input gets dropped. The mig-docs SOP `sops/entity-status.md:26` says a pin re-run needs a direct Lambda invoke. Seen in prod, 2026-10-14: 2 failed executions (migrate + undo) on one entity, and 3 prod entities carried FAILED/no-newId payment-account rows.
- **Fix**: first fix whatever made the mint fail (otherwise Phase 0 fails again after the pin). Then direct-invoke `mig-fin-mg-fun` once with `currencyPin`. The gate SUPPLY path persists a durable `mxpin_fin_` pin before any work. Then `start-execution` with the original input. Long-term: forward `$.currencyPin` in the SFN Payload, or correct the remediation text.
- **Gotcha (confirmed in prod, 2026-10-14)**: the direct pin invoke skips the SFN's copy step (mig-copy-mg-fun: transform `outbound/` → migration-bucket `inbound/`), so it loads the stale `inbound/<id>/` copies. A source-data fix made after the last copy won't be in that invoke's Phase 0. Expect the invoke to set the pin and still fail the mint (`FunctionError: Unhandled`, same `sourceHash`). The follow-up `start-execution` re-copies and picks up the fix. Phase 0 takes the Stripe address from `invoices.json` `reference.entityLocations[].physicalAddressId` first (`phase0-config-loader.ts:721`), and `entity.json` only as a fallback, so verify the fix in the financials export.
- **Gotcha 2 (prod, 2026-10-14)**: after the source address is fixed, the next mint fails with fin-stripe-fun `Keys for idempotent requests can only be used with the same parameters they were first used with … 'fb-classic:<act>:<entity>:payment-account:<entity>#createStripeAccount'`. The Stripe idempotency key is deterministic and doesn't depend on the payload. Stripe keeps the bad-address attempt's key for at least 24 h, so a corrected payload under the same key is refused. Retry only after 24 h have passed since the last bad-param mint, and don't send any more bad-param attempts in the meantime.

## 13. `ImportParts` `AccessDeniedException` `dynamodb:UpdateItem` on `mig-migration-common-iac` (IAM drift past dev)

- **Signature**: `ImportParts` fails `AccessDeniedException … assumed-role/mig-prt-mg-fun … not authorized to perform: dynamodb:UpdateItem … no identity-based policy allows`, trace at `conditionHeld`. Hits re-runs where `mxpin_prt_<entityId>` already exists. A first run only uses PutItem.
- **Root cause**: `mig-prt-mg-fun` `terraform/iam.tf` has granted `UpdateItem` since `3aeebe9` (DP-112, 2026-09-15). The live inline policy `mig-prt-mg-fun-dynamodb-migration-mapping-access` has it only in **dev**. Stage, prod and demo lack it while running code `138a647`, which sends `UpdateCommand`. So the code was promoted but the IAM change wasn't. Confirmed 2026-10-14 on a prod re-run.
- **Fix**: apply `mig-prt-mg-fun` Terraform in stage/prod/demo (find out why promotion didn't apply IAM). Prod is a hand-off, not a self-run.
